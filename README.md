# DevOps Quality Gates — гипотетическая трубa

Документ описывает набор quality gates (QG) для условного pipeline разработки
и доставки приложения. QG разнесены по трём этапам конвейера:

- **CI** — Continuous Integration (сборка, проверки на уровне кода и артефакта).
- **CDL** — Continuous Delivery (доставка на тестовые / preprod-стенды,
  интеграционные и нефункциональные проверки).
- **CDP** — Continuous Deployment to Production (выкат в прод, валидация
  продовой среды и post-deploy наблюдение).

Каждый QG идёт под идентификатором вида `QG.<этап>.<номер>` (формат взят из
презентации `docs/QG (1).pdf`) и кратко описан в стиле «<Имя> представляет
собой <описание>». Если хотя бы один блокирующий gate падает — пайплайн
стопается, артефакт дальше не едет.

---

## Работоспособность

В репозитории помимо описания QG лежит **рабочий мини-сервис** и **боевая
обвязка пайплайна**, чтобы каждый gate из таблиц ниже имел исполнение.

### Структура репозитория

```
.
├── app/                    # пакет приложения (HTTP-сервис на stdlib)
│   ├── __init__.py
│   ├── greeter.py          # бизнес-логика — формирование приветствия
│   └── server.py           # http.server с /healthz, /readyz, /version, /hi
├── tests/                  # pytest: юнит + интеграционные тесты ручек
├── deploy/
│   ├── helm/               # Helm-чарт сервиса (Deployment, Service, HPA)
│   └── k8s/                # неймспейсы и Argo Rollouts (canary)
├── scripts/
│   ├── smoke.sh            # smoke-тесты для staging/prod
│   └── perf.js             # k6-сценарий нагрузки
├── .github/workflows/
│   ├── ci.yml              # CI: lint, SAST, SCA, build, scan, sign
│   ├── cdl.yml             # CDL: deploy to staging, BVT/ST/IFT, DAST, LT
│   └── cdp.yml             # CDP: approval, canary, soak, rollback
├── docs/QG (1).pdf         # презентация-первоисточник (формат и часть гейтов)
├── Dockerfile              # multi-stage, non-root, slim
├── pyproject.toml          # деки + конфиги ruff/mypy/pytest/coverage
├── Makefile                # локальные команды-обёртки над CI
├── .pre-commit-config.yaml # сетка локальных хуков
├── .gitleaks.toml          # конфиг secret-сканера
├── .markdownlint.yaml      # конфиг markdownlint
├── commitlint.config.js    # Conventional Commits
├── CODEOWNERS              # требуемые ревьюеры
└── main.py                 # сохранён для совместимости (`python main.py`)
```

### Запуск

```bash
# 1. Создать виртуалку и поставить зависимости
make venv && make install

# 2. Локальные проверки (зеркало CI-этапов)
make lint     # ruff
make type     # mypy
make sec      # bandit (SAST)
make audit    # pip-audit (SCA)
make test     # pytest + coverage (порог 80%)

# 3. Запуск сервиса
make run                       # python -m app.server
python main.py                 # совместимый запуск, выведет: Hi, PyCharm

# 4. Контейнер
make docker-build              # multi-stage образ
make docker-run                # доступен на localhost:8080
./scripts/smoke.sh             # прогон smoke против локального контейнера
```

Сервис поднимает HTTP на `:8080`:

| Ручка                  | Что делает                                                |
|------------------------|-----------------------------------------------------------|
| `GET /healthz, /livez` | liveness, всегда `{"status":"ok"}` если процесс жив       |
| `GET /readyz`          | readiness, `{"status":"ready"}`                            |
| `GET /version`         | возвращает версию из `app.__version__`                     |
| `GET /hi?name=...`     | основная ручка: `{"message":"Hi, <name>"}` или 400         |

### Что покрыто прямо сейчас (локально, без CI-инфры)

- 12 тестов (`pytest`) — юнит + интеграционные HTTP-тесты, **coverage 83%**.
- `ruff check` и `ruff format --check` чистые.
- `mypy --strict` без ошибок.
- Helm-чарт линтуется (`helm lint deploy/helm`) и рендерится в валидный YAML.
- Все workflow-yaml проходят `yamllint`.

### Где исполняются QG из таблиц

| Этап | Кто исполняет                          | Файл                              |
|------|----------------------------------------|-----------------------------------|
| CI   | GitHub Actions                          | `.github/workflows/ci.yml`        |
| CDL  | GitHub Actions + Helm + k6 + ZAP        | `.github/workflows/cdl.yml`       |
| CDP  | GitHub Actions + Argo Rollouts          | `.github/workflows/cdp.yml`       |

Имена job'ов в workflow начинаются с идентификатора QG (`QG.CI.3 SAST`,
`QG.CDL.10 LT`, `QG.CDP.8 Canary` и т.д.) — так в UI Actions сразу видно,
какой gate за что отвечает.

> Часть «больших» проверок (API META, Pact-broker, BVT/ST/IFT на реальных
> стендах, Pen-test, Vault rotation) в demo-репе оставлены как
> `echo "::notice::..."` — это маркер места, куда в реальной инфре
> подключается соответствующий сервис.

## Этап CDL (Continuous Delivery)

Триггерится после успешного CI. Цель — задеплоить артефакт на dev / staging /
preprod и прогнать на нём всё то, что не проверяется статикой и юнитами:
системное тестирование (ST), интеграционно-функциональное (ИФТ), нефункциональные
(нагрузка, безопасность).

## Сводно

```
push ──► [CI: 25 gates] ──► [CDL: 28 gates] ──► [CDP: 28 gates] ──► prod
                ▲                  ▲                   ▲
            быстрые           BVT / ST / ИФТ      безопасный
            проверки          + DAST + LT         выкат + soak
            кода/арт.         на стенде           + auto-rollback
```

Любой gate может быть **блокирующим** (красное — пайплайн стоп) или
**информационным** (предупреждение, релиз едет дальше). Конкретное разделение —
вопрос политики команды и зрелости пайплайна; в презентации `docs/QG (1).pdf`
часть гейтов помечена как «обязательный QG на этапе CI/CDL/CDP» — те же
гейты блокирующие и в этом репозитории.
